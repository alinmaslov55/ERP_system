Request lifecycle example

When a warehouse operator receives 20 units of a product:

    React submits the receiving form to the Laravel API.

    Laravel authenticates the user and checks permissions.

    A request validator checks the product, warehouse and quantity.

    A receiving service starts a database transaction.

    The application records the receipt and stock movement and updates the stock balance.

    The transaction commits only if all operations succeed.

    Laravel returns the updated receipt and stock balance.

    React refreshes the relevant product, warehouse and dashboard queries.

The frontend must never be trusted to determine the actual stock balance or authorize an operation. Those rules belong on the backend.

Use separate tables for order headers and line items. A purchase order with five products should have one header and five item records, not five independent purchase orders.
Important database rules

    SKU should be unique within the appropriate business scope.

    Use foreign keys to prevent invalid relationships.

    Use NUMERIC/DECIMAL for monetary amounts, never floating-point types.

    Use integer quantities for indivisible items; support decimal quantities only when the selected unit requires them.

    Use database transactions for operations that change inventory.

    Add indexes to frequently filtered columns, including SKU, status, dates and foreign keys.

    Use soft deletion or archiving for products that have historical transactions.

An important design decision: inventory_balances is a current-state projection, while stock_movements is the historical record. Every stock-changing operation must update both consistently. Historical movements should not be casually edited or deleted to correct a mistake; create a reversing movement and an adjustment instead.
6. The critical business logic

These rules distinguish a serious ERP from a basic database application.
A. Inventory calculations

For a product in a particular warehouse:
Available stock=On-hand stock−Reserved stock
Available stock=On-hand stock−Reserved stock

Example:

Quantity

On hand
	

100

Reserved for sales
	

25

75

Result
	

Reject or require a supported backorder

Never allow concurrent orders to reserve more units than are available.
B. Purchase order workflow
Draft
Submitted
Partially received
Received

A submitted order does not increase stock. Only confirmed goods receipt events increase inventory.

Example: you order 100 keyboards and receive 60 today. The system records a receipt of 60. The outstanding quantity remains 40. When the remainder arrives, another receipt completes the order.
C. Sales order workflow
Draft
Confirmed
Reserved
Fulfilled

Confirmation validates availability; reservation protects stock; fulfillment records the physical issue. Cancellation must release any outstanding reservation.
D. Prevent race conditions

Imagine two sales operators try to reserve the last five units simultaneously.

Use a database transaction and appropriate row locking or an atomic conditional update so only one request can successfully reserve the available stock. Enforce the invariant in the database where practical, not only through frontend checks.
E. Inventory valuation

For the initial release, use weighted-average cost or a clearly documented simpler valuation policy. Weighted-average costing is a useful learning objective:
New average cost=Old stock value+Receipt valueOld quantity+Received quantity
New average cost=Old quantity+Received quantityOld stock value+Receipt value​

You should define how returns, stock adjustments and negative inventory affect valuation before implementing the full accounting behavior.

## 5. Architecture

Use a **modular monolith**: one Laravel backend, one React frontend, and one PostgreSQL database. This provides clear boundaries without the operational overhead of microservices.

```text
React + TypeScript
  ├── Pages
  ├── Reusable components
  ├── Forms and tables
  ├── Charts
  └── API client / TanStack Query
          │
          │ HTTP + JSON
          ▼
Laravel REST API
  ├── Routes
  ├── Authentication
  ├── Form Requests / validation
  ├── Policies / authorization
  ├── Controllers / Resources
  ├── Application services
  ├── Domain rules
  └── Database transactions
          │
          ▼
PostgreSQL
  ├── Relational tables
  ├── Foreign keys and constraints
  ├── Indexes
  └── Inventory records

Docker Compose
  ├── Frontend
  ├── Backend
  ├── PostgreSQL
  └── Redis / worker when needed
```

### Example request lifecycle: receiving 20 units

1. React submits a goods-receipt form to the Laravel API.
2. Laravel authenticates the user and checks permissions.
3. A request validator checks the product, warehouse, and quantity.
4. A receiving service starts a database transaction.
5. The application records the receipt and stock movement and updates the stock balance.
6. The transaction commits only if all operations succeed.
7. Laravel returns the receipt and updated stock balance.
8. React refreshes the affected product, warehouse, and dashboard queries.

The frontend must never be trusted to calculate authoritative stock balances or authorize an operation. These rules belong on the backend.

### Main relationships

- A category has many products.
- A product can have balances in multiple warehouses.
- A warehouse has balances for many products.
- A product and warehouse pair has one current inventory balance.
- A product can have many stock movements.
- A supplier can have many purchase orders.
- A purchase order has many purchase order items.
- A purchase order can have multiple goods receipts.
- A goods receipt has multiple receipt items.
- A customer can have many sales orders.
- A sales order has many sales order items.
- A sales order can have fulfillment records.
- Users perform and are recorded against important business operations.

### Important database rules

- Enforce SKU uniqueness within the relevant business scope.
- Use foreign keys to prevent invalid relationships.
- Use `NUMERIC`/`DECIMAL` for monetary amounts, never floating-point types.
- Use integer quantities for indivisible items; allow decimal quantities only for units that require them.
- Use transactions for operations that change inventory.
- Index commonly filtered columns, including SKU, status, dates, and foreign keys.
- Archive products that have historical transactions instead of deleting their history.
- Store timestamps consistently and define the business timezone for reports and documents.

### Inventory balance versus stock movements

`inventory_balances` represents current state. `stock_movements` is the historical record.

Every stock-changing operation must update both consistently within a database transaction. Do not casually edit or delete historical movements to correct a mistake; record a reversing movement or an explicit adjustment.

## 7. Critical Business Logic

### 7.1 Available stock

For a product in a warehouse:

```text
Available stock = On-hand stock - Reserved stock
```

Example:

| Measurement | Quantity |
|---|---:|
| On-hand | 100 |
| Reserved | 25 |
| Available | 75 |
| Requested order | 80 |
| Result | Reject or use an explicitly supported backorder workflow |

### 7.2 Purchasing workflow

- A draft order can be edited.
- A submitted order is awaiting goods.
- Receiving 60 units from an order of 100 increases inventory by 60.
- The remaining quantity is 40.
- A later receipt can complete the order.
- Receiving the same request twice must not duplicate stock.

### 7.3 Sales workflow

- Validate product and warehouse availability.
- Reserve stock when the order reaches the appropriate state.
- Fulfillment records the actual stock issue.
- Cancellation releases any remaining reservation.
- Invalid status transitions must be rejected by the backend.

### 7.4 Concurrency and race conditions

Two sales operators might attempt to reserve the last five units simultaneously. Use a database transaction with suitable row locking or an atomic conditional update so that only one request can reserve the available stock. Do not rely only on a frontend availability check.

Consider idempotency for operations that may be retried, especially receiving, fulfillment, and payment recording. A repeated request must not accidentally apply the same business operation twice.

### 7.5 Inventory valuation

For an initial advanced feature, consider weighted-average cost:

```text
New average cost =
    (Old stock value + Receipt value)
    / (Old quantity + Received quantity)
```

Define how returns, adjustments, and negative inventory affect valuation before implementing this feature. Keep costing rules documented and tested.
